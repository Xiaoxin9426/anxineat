# 项目概述

## 背景与目标

以蜜雪冰城小程序的公开功能表现为**产品参照**，从零复刻一套可运行、可验收、可继续迭代的点餐小程序。鉴于商标与版权合规要求，本项目不复用「蜜雪冰城」品牌名、雪王 IP 与官方素材，自建品牌 **「安心饮 / Anxineat」**，使用通用化商品名（如「冰鲜柠檬水」）、占位图或留空图片，**仅做风格近似**。

**产品目标**：交付覆盖「选店 → 点单 → 定制 → 下单 → 支付 → 取餐/配送 → 核销」完整闭环的点餐小程序（用户端，原生微信小程序）\+ 商家管理后台（单文件 Web 控制台）\+ 后端服务（Spring Boot 3），并内置会员积分与优惠券营销体系。

**成功标准**：核心链路端到端跑通；订单、金额、优惠计算准确且可复核；具备可运营的商家后台；关键质量指标达到本文第五部分门槛。

## 非目标（本期明确不做）

- 不做供应链、进销存与总部门店结算系统。
- 不做总部级多租户 SaaS；本项目为「单商户多门店」模型。
- 不做自建骑手调度系统；外卖配送以状态模拟为主，预留第三方配送接口。
- **不使用蜜雪冰城官方商标、IP 形象与受版权保护的素材**；品牌名与视觉仅做「风格近似」。
- 不做原生 App 与支付宝端小程序（仅预留多端扩展）。

## 术语表

|术语|定义|
|---|---|
|门店（Store）|可独立营业、独立点单与出餐的线下实体门店，支持自取和/或外卖。|
|商品（Product）|可售卖单品（如「冰鲜柠檬水」），归属一个分类，经 `store_product` 关联在若干门店售卖（**不直接挂 store_id**）。|
|规格组 / 规格项|商品可定制维度（甜度、冰度、温度、杯型）及其选项（如 5 分糖、去冰、中杯）。`CUP` 规格组为「库存维度组」，其选项与 SKU 杯型一一对应。|
|小料（Topping）|可加购配料（珍珠、椰果等），可多选，影响价格。|
|SKU|商品 \+ 杯型组合的唯一售卖单元，库存与价格载体（甜度/冰度/温度不进 SKU）。|
|购物车（Cart）|下单前暂存用户所选商品及定制项的集合，**落库**按 `user_id + store_id` 隔离（非 Redis）。|
|订单（Order）|一次交易记录，含明细、金额、优惠、状态，绑定门店与用户。|
|取餐码|自取订单支付成功后生成的取餐凭证（按「门店 \+ 当日」唯一），用于门店核销。|
|优惠券（Coupon）|满足条件后可抵扣订单金额的权益凭证，分无门槛/满减/折扣等类型。|
|积分（Point）|会员通过消费、签到等获得的权益数值，可兑换优惠券；余额 = 累计获得 − 累计使用 − 累计过期。|
|核销（Redeem）|门店确认订单已完成（自取核销取餐码 / 外卖确认送达）的动作。|
|幂等|同一操作（支付回调、领券、下单）重复请求只生效一次，由数据库唯一索引保障。|

# 用户与核心场景

## 目标用户

- **到店顾客**：希望快速下单、减少排队，到店即取。
- **外卖用户**：希望远程下单，配送到指定地址。
- **店员 / 门店运营**：通过商家后台接单、出餐、核销与维护商品。
- **运营 / 管理端**：配置优惠券、积分规则与门店信息（由超管账号承担）。

## 核心用户故事（含验收要点）

|用户故事|验收要点|
|---|---|
|作为到店顾客，我选店、浏览菜单、定制并加购，提交自取订单并支付，到店凭取餐码取餐。|选店后看到该店可售商品与售罄状态；定制项齐全；支付成功生成取餐码；订单进入制作队列。|
|作为外卖用户，我选收货地址与送达时段，提交外卖订单并支付，查看配送状态。|地址必填校验；支持预约送达时段；配送状态可查看；送达后订单完成。|
|作为会员，我消费得积分、签到再得积分，并用积分兑换优惠券。|消费积分按规则入账；签到每日一次防重复；兑换后券进入「我的优惠券」且可用。|
|作为店员，我在后台上下架商品、维护库存、接单并核销订单。|商品变更即时生效；订单流转「接单/制作/出餐」；取餐码可核销；金额与报表一致。|

# 功能需求

## 首页与门店选择

**需求描述**：小程序冷启动进入欢迎页（约 2 秒），随后进入首页。首页自上而下含：营销 Banner 区、会员积分信息卡、居中「立即点餐」主入口、营销活动区。用户可授权定位获取附近门店；未授权时可手动搜索或选择城市门店。门店列表展示距离、营业状态（营业中/休息中）、支持渠道（自取/外卖）与**起送价/配送费/满额免配信息**。默认选中距离最近且营业中的门店。

**验收标准**：

1. 冷启动欢迎页约 2 秒自动进入首页，可跳过。
2. 定位授权成功后，门店列表按距离升序排列并展示距离与营业状态。
3. 未授权定位时，提供城市选择与门店搜索，可正常进入点餐。
4. 休息中或当前渠道不可用的门店不可下单，界面明确提示。
5. 首页 Banner、积分信息、点餐入口与活动区四个区块均可点击进入对应页面。

## 菜单与商品

**需求描述**：点餐页展示当前门店菜单，支持按分类切换；商品卡片展示图片、名称、价格、销量/推荐标签与售罄状态。提供关键词搜索与「人气推荐」排序。商品详情页展示图片、名称、价格、规格选项、小料列表、商品描述与热量。已售罄商品置灰且不可加入购物车。

**验收标准**：

1. 分类切换、搜索、排序均只返回当前门店可售商品。
2. 售罄商品展示「售罄」标记，且无法加入购物车或下单。
3. 商品详情展示全部已配置规格与小料，选择项齐全后价格正确联动。
4. 商品图片加载失败时有占位图，不阻断流程。

> **品牌合规**：商品名与图片均为「安心饮」自有素材；不出现任何第三方品牌标识。

## 规格定制与购物车

**需求描述**：商品支持多规格组定制（甜度、冰度、温度、杯型），每组必选一项；`CUP` 组决定 SKU（库存维度）。小料可多选并逐项加价。同一商品的不同规格组合视为不同购物车条目（条目指纹 `item_key`）。购物车按当前门店隔离（切换门店提示并清空或转换）。购物车支持改量、删除、清空、改定制项，并实时汇总总价与优惠预估。

**验收标准**：

1. 规格组必选项未选全时，商品不可加入购物车（返回「请选择杯型」等明确提示）。
2. 同一商品不同规格在购物车中为不同条目，可分别增减。
3. 小料数量可增减，小料价格正确计入条目价与合计。
4. 切换门店时给出明确提示，确认后清空原门店购物车。
5. 购物车合计金额 = 各条目（商品价 \+ 小料价）之和，误差为 0（分单位整数运算）。

## 下单与支付

**需求描述**：用户从购物车进入确认订单页，选订单类型（到店自取 / 外卖）。自取需选取餐门店（默认当前）与预计到店时间（立即/预约）；外卖需选收货地址与期望送达时段。确认页展示商品明细、优惠明细（满减/优惠券/积分抵扣/等级折扣）、配送费（外卖）、应收金额。提交订单后：校验门店营业、商品在售与库存、金额与优惠有效性；生成「待支付」订单（资源占用：券 `LOCKED`、库存预占）；拉起支付。**支付成功由回调通知，后端验签/模拟校验 + 幂等后订单流转「已支付」**。支付超时（默认 15 分钟）由定时任务自动取消并释放券与库存。

**验收标准**：

1. 应收金额 = 商品总额 \+ 配送费 − 优惠总额（券 \+ 积分 \+ 等级折扣），分与元精度正确，无四舍五入差错（前端只展示不计算）。
2. 提交订单时若商品已售罄/库存不足/门店休息/未达起送金额，返回明确错误且不生成订单。
3. 支付回调重复到达时，订单只处理一次（以 `pay_no` 唯一索引幂等）。
4. 支付超时未支付，订单自动取消，优惠券退回（`LOCKED→UNUSED`）、库存回补。
5. 自取订单支付成功后立即生成唯一取餐码（按「门店 \+ 当日」唯一）。

## 订单管理

**需求描述**：用户「我的订单」按状态分组展示全部订单。订单详情展示商品明细、定制项、金额明细、优惠明细、门店/地址、订单状态与时间线（待支付→已支付→制作中→待取餐/配送中→已完成）。自取展示取餐码与制作进度；外卖展示配送状态。支持「再来一单」（按历史订单重建购物车，原商品已售罄则跳过并提示）。

**验收标准**：

1. 订单状态流转严格符合本文「订单状态机」定义，非法流转被拒绝（经 `OrderStatus.assertTransition` 校验）。
2. 取餐码在订单详情显著展示，可放大查看。
3. 「再来一单」重建购物车时，若原商品已售罄则跳过并在界面提示。

## 会员与积分

**需求描述**：支持手机号验证码 / 微信授权登录，未登录用户可在下单前以游客身份点单，支付前引导登录。会员体系含等级（普通/银卡/金卡，按累计实付金额升级，配置项可调）与积分账户。积分获取：消费 1 元积 1 分（可配置）、每日签到得固定积分；积分可兑换指定优惠券。积分变动写入流水，支持查询明细。

**验收标准**：

1. 同一手机号只能绑定一个会员账户；微信 `open_id` 与手机号各自唯一，支持「先微信静默登录 → 后补绑手机号」。
2. 消费积分按订单实付金额计算并即时入账；退款时按比例扣回（`REFUND_ROLLBACK`）。
3. 签到每日仅一次，跨天重置，重复签到被拒绝（以 `last_signin_date` 防重）。
4. 积分兑换扣减与优惠券发放在同一事务内完成（`USE_EXCHANGE`）。
5. **积分余额 = 累计获得 − 累计使用 − 累计过期**，`user.point_balance` 与 `point_record` 流水对账一致（见附录 C-1）。

> 积分余额由「流水实时快照」维护：`user.point_balance` 为当前可用积分，`user.point_total` 为累计获得积分（用于对账）。过期扣减记 `EXPIRE` 流水。

## 优惠券与营销

**需求描述**：优惠券支持三种类型：无门槛券（立减固定金额）、满减券（满 X 减 Y）、折扣券（如 9 折，设最高抵扣）。券属性含：可用商品范围（全场/指定分类/指定商品，经 `coupon_scope` 子表）、适用渠道（自取/外卖，`channels`）、有效期、每人限领数量、`stackable`（能否与会员等级折扣叠加，默认不叠加）。提供「领券中心」、用户「我的优惠券」（未使用/已占用/已使用/已过期）。下单时可选用一张可用券，单笔最多用一张；券与秒杀/特殊活动互斥（规则可配）。后台可创建、停用券模板。

**验收标准**：

1. 下单时仅展示当前订单可用的券；满足门槛与渠道/范围条件方可使用。
2. 同一张券同一订单只能使用一次；并发下单时一张券只会被一张订单占用（`user_coupon.version` 乐观锁 + `LOCKED` 态，防并发）。
3. 订单取消/退款时，已占用（`LOCKED`）券退回 `UNUSED` 可再用；已核销（`USED`）券按规则处理。
4. 过期券不可用，状态准确展示「已过期」。

> **用户券状态机**：`UNUSED` → `LOCKED`（下单占用，待支付）→ `USED`（支付成功核销）；任意非 `USED` 态可被 `EXPIRED` 覆盖。原文档仅三态（`UNUSED/USED/EXPIRED`）无法区分「占用未支付」与「真正在用」，会导致超时取消时无法判断该不该退回——故增加 `LOCKED` 态（见附录 C-9）。

## 个人中心

**需求描述**：展示用户头像昵称、会员等级与积分、常用入口（我的订单、优惠券、积分明细、收货地址、常用门店）、联系客服与设置。

**验收标准**：各入口可达且数据正确；未登录状态展示登录引导。

## 商家管理后台

**需求描述**：后台为**单文件 Web 控制台**（`backend/src/main/resources/static/admin/index.html`，约 81KB，无需独立前端工程），按角色区分：超管（多门店，可切换 `effectiveStoreId`）、店员（单门店，`store_id` 绑定）。核心能力：商品管理（增删改、上下架、分类维护、规格与小料配置、库存与售罄开关）、订单管理（按门店/状态筛选、接单、标记制作、出餐、核销取餐码、退款操作）、门店管理（营业状态、营业时间、自取/外卖开关、配送费、起送价）、营销配置（优惠券模板、积分规则、Banner）、基础数据概览（今日订单数、销售额、客单价）。

**验收标准**：

1. 店员只能看到并操作本门店数据（`AdminPrincipal.effectiveStoreId` 越权拦截）；超管可切换门店。
2. 商品上下架与库存修改在用户端即时生效（含售罄标记，经 `store_product.sold_out` 与 SKU `stock`）。
3. 核销时输入取餐码，校验该码属于本门店、当日、未核销，成功后订单置为已完成（`COMPLETED`）。
4. 后台今日数据 = 订单表统计结果，可复核。

# 关键业务流程

## 下单流程（自取 / 外卖）

用户端一次完整下单时序如下（自取与外卖差异在地址与配送环节）：

1. **进入确认页**：`GET /api/order/preview`（携带 `storeId`、购物车条目 `itemKey` 列表、`specOptionIds`、`toppingIds`、`userCouponId`、`usePoint`）做金额与优惠试算（服务端重算，不信任前端）。
2. **提交订单**：`POST /api/order`（携带 `idempotent_key`）。服务端依次：校验门店营业（手动开关 ∧ 营业时间）、商品在售、SKU 库存、起送金额、地址（外卖必填）；以 `idempotent_key` 唯一索引防并发双写；占用券（`UNUSED→LOCKED`，`version` CAS）、预占库存；生成 `PENDING_PAYMENT` 订单与 `order_item` 快照（含 `product_image` / `spec_text` / `topping_text`）；写入 `expire_time = now + 15min`。
3. **拉起支付**：`POST /api/pay/create` 生成 `pay_no`（`MOCK` 或 `WECHAT_JSAPI` 预支付参数）。
4. **支付成功**：模拟回调 `/api/pay/mock/callback`（或微信 `/api/pay/callback`）携带 `pay_no` 与金额；以 `uk_pay_no` 幂等；事务内更新 `payment` 与订单 `PENDING_PAYMENT→PAID`，自取生成 `pickup_code`，占用券 `LOCKED→USED`，发放消费积分（`EARN_CONSUME`，`biz_no=订单号` 防重）。
5. **超时释放**：定时任务扫描 `status=PENDING_PAYMENT AND expire_time<now`，取消订单（`CANCELLED`），券 `LOCKED→UNUSED` 退回，库存回补。

## 订单状态机

订单状态全集与合法迁移如下，**任何不在此迁移集合内的状态变更必须被拒绝**（实现见 `OrderStatus.assertTransition`）：

```text
PENDING_PAYMENT ──支付成功──▶ PAID ──店员接单──▶ MAKING ──出餐──▶ READY
       │                       │                   │                │
       │                       │                   │                ├──(自取) 核销取餐码 ─▶ COMPLETED
       │                       │                   │                └──(外卖) 开始配送 ──▶ DELIVERING ─▶ COMPLETED
       │                       │                   │
       │                       └──退款─────────────┴────────────────────────────────▶ REFUNDED
       └──用户取消 / 15 分钟超时未支付 ─▶ CANCELLED
```

- **状态集**：`PENDING_PAYMENT` 待支付、`PAID` 已支付、`MAKING` 制作中、`READY` 待取餐/待配送、`DELIVERING` 配送中、`COMPLETED` 已完成、`CANCELLED` 已取消、`REFUNDED` 已退款。
- **终态**：`COMPLETED` / `CANCELLED` / `REFUNDED`，终态不可再迁移。
- **订单时间线渲染**：`orders` 表补齐 `paid_at / accepted_at / ready_at / delivering_at / completed_at / cancel_at / refunded_at`，并写入 `order_status_log` 供详情页展示。

## 优惠券规则

|规则项|约定|
|---|---|
|使用条件|满足金额门槛、商品范围（`coupon_scope`）、适用渠道（`channels`）、有效期；同订单最多用 1 张。|
|抵扣计算|满减/无门槛按金额立减；折扣券按实付基数打折并受 `max_discount` 上限约束；均不参与配送费减免；与等级折扣是否叠加由 `stackable` 决定（默认不叠加）。|
|核销时机|下单成功即 `LOCKED` 占用；支付成功转 `USED`；支付失败/取消则退回 `UNUSED`。|
|退款处理|全额退款且券未过期 → 退回可再用；否则券作废（`EXPIRED`）。|
|并发安全|用户券核销使用数据库乐观锁（`version` 条件更新），避免超发与重复核销。|

## 积分规则

|规则项|约定|
|---|---|
|消费积分|每实付 1 元积 1 分（取整），支付成功后入账（`EARN_CONSUME`）；退款按比例扣回（`REFUND_ROLLBACK`）。|
|签到积分|每日签到 \+N 分（可配置，存 `sys_config`），同一自然日仅一次（`last_signin_date` 防重）。|
|积分兑换|按 `point_cost` 扣除积分（`USE_EXCHANGE`）并发放对应优惠券，同一事务完成。|
|积分有效期|支持年度滚动过期（规则后台可配置）；过期记 `EXPIRE` 流水，使余额与流水始终可对账。|
|余额口径|**余额 = 累计获得 − 累计使用 − 累计过期**（`user.point_balance` 为当前可用，`user.point_total` 为累计获得）。|

# 非功能需求

## 性能

- 首页、门店列表、菜单等读接口 P95 < 300ms；下单接口 P95 < 1s（不含支付拉起）。
- 支持单店高峰期约 100 并发下单不产生金额/库存错误；并发安全由数据库 CAS + 唯一索引保障（无 Redis 依赖）。
- 商品图片走对象存储（本期占位/留空），弱网下有加载降级。

## 安全与合规

- 登录态使用 JWT（短期 token），敏感接口鉴权（`Authorization: Bearer <token>`，`type=USER/ADMIN`）。
- 支付回调必须验签/模拟校验，且回调处理幂等（`pay_no` 唯一索引）；密钥不落前端、不进日志；支付流水**不存原始回调报文**，仅存 `transaction_id` 等非敏感要素。
- 接口层做参数校验、防 SQL 注入、防越权（订单/门店归属校验，`AdminPrincipal.effectiveStoreId` 越权拦截）。
- 用户手机号等按最小必要采集，提供隐私政策；按《个人信息保护法》告知与授权。
- 管理员后台具备鉴权与角色隔离（超管/店员）。

## 可用性与兼容性

- 兼容主流 iOS / Android 微信版本；页面适配 375px 基准与刘海屏安全区。
- 弱网与接口异常时有重试与友好提示，不出现白屏或死循环。
- 服务具备基本监控（日志、错误上报），关键链路可排查。

                                                      │ JDBC

## 关键机制设计

|机制|设计|验收关注点|
|---|---|---|
|购物车|**落库**（MySQL `cart_item`，`user_id+store_id` 隔离），`uk_cart_line` 唯一索引 upsert；游客车登录后用唯一键合并|切换门店隔离；游客登录合并不丢项；无 Redis 依赖|

|订单超时|定时任务扫描 `status=PENDING_PAYMENT AND expire_time<now`，取消并回补资源|超时自动取消且资源正确回补|

# 验收标准（端到端用例清单）

1. 新用户：定位选店 → 浏览菜单 → 定制商品 → 加购 → 提交自取订单 → 支付成功 → 生成取餐码 → 后台核销 → 订单完成。
2. 外卖链路：选地址 → 提交外卖订单 → 支付 → 配送状态流转 → 确认送达 → 完成。
3. 金额正确性：多商品 \+ 小料 \+ 优惠券组合，服务端金额与前端一致，分位精确。
4. 售罄与库存：SKU 售罄后菜单标记、不可下单；并发下单不超卖。
5. 支付回调幂等：同一回调重复投递，订单与支付状态只变更一次。
6. 订单超时：待支付订单 15 分钟自动取消，券退回、库存回补。
7. 优惠券并发：同券并发下单只占用一次。
8. 积分：消费积分入账、签到防重、兑换发券、退款扣回，余额与流水一致（含过期对账）。
9. 后台权限：店员仅见本门店数据，超管可跨店。
10. 异常恢复：弱网重试、接口失败提示、支付失败可重新发起。

## 附录 C：修订记录（原文档不合理处逐条修正）

> 以下每条对应 `db/schema.sql` 内联「修正点」注释与相应实体/枚举的 JavaDoc。原文档指 `../蜜雪冰城点餐小程序复刻 — 需求规格与技术实现方案.md`。

### C-1 积分余额口径矛盾（高，已修正）
- **原文档**：验收标准 5「积分余额 = 累计获得 − 累计使用」；积分规则又要求「默认年度滚动过期」。
- **问题**：存在过期机制时该等式不成立，余额与流水无法对账。
- **修正**：余额 = 累计获得 − 累计使用 − 累计过期；`point_record` 新增 `EXPIRE`（及 `ROLLBACK_DEDUCT`/`ADMIN_ADJUST`）流水类型；`user` 表以 `point_balance`（当前可用）与 `point_total`（累计获得）双字段对账。本文「积分规则 / 会员与积分验收标准 5」已就地更新。

### C-2 order_item 缺图片与可读文本快照（高，已修正）
- **原文档**：`order_item` 仅 `product_name / sku_snapshot / toppings_snapshot`，无图片列。
- **问题**：商品下架/改图后订单详情页图片丢失；规格/小料仅 JSON，前端展示需二次解析。
- **修正**：补 `product_image`（下单时快照）、`spec_text`、`topping_text`（下单时快照可读文本）。见 `OrderItem.java` 与 `schema.sql` order_item 注释。本文数据模型表已补列。

### C-3 营业状态双控制关系未定义（高，已修正）
- **原文档**：`store` 同时有 `business_status` 与 `business_hours` 单字段，未定义关系。
- **问题**：无法判定「手动休息但仍在营业时间」或「营业时间内但手动休息」是否可下单。
- **修正**：约定 **「可下单 = business_status=1（营业中）∧ 当前时间在 store_business_hours 覆盖时段内」**。手动总开关优先；营业时间拆 `store_business_hours` 子表（按星期多时段、支持跨零点）。本文「术语表 / 门店」与下单流程已明确。

### C-4 金额精度与折扣表达（高，已修正）
- **原文档**：金额字段未明确单位，折扣用「0.9/0.85」类小数。
- **问题**：浮点参与金额计算会出现 0.1+0.2 类精度误差，且与券叠加时不可复核。
- **修正**：所有金额字段 `BIGINT`（分）；折扣用 `INT` **万分比**（10000=不打折，9000=9 折）。`member_level.discount`、`coupon_template.discount` 均改为万分比。本文数据模型表与「关键机制设计 / 金额一致性」已统一。

### C-5 product 多门店关系表达错误（高，已修正）
- **原文档**：`product` 表带 `store_id` 单列，术语表却定义「商品可在若干门店售卖」。
- **问题**：一对多关系用单列无法表达。
- **修正**：移除 `product.store_id`，改 `store_product` 关联表（支持门店加价 `price_diff`、门店独立售罄 `sold_out`、门店独立上下架）。本文术语表与数据模型表已更新。

### C-6 售罄状态三源归一（中，已修正）
- **原文档**：同时存在 `product.sold_out`、`product_sku.stock`、`product_sku.status` 三个状态源，无统一口径。
- **问题**：易不一致，菜单「售罄」判定歧义。
- **修正**：约定「实际可售 = 手动开关 `sold_out=0` ∧ 该门店 `store_product.sold_out=0` ∧ 至少一个 SKU `stock>0`」；`product_sku.status` 仅保留「SKU 停用」语义。本文「菜单与商品 / 规格定制与购物车」验收标准已对应。

### C-7 购物车强依赖 Redis（中，已修正）
- **原文档**：购物车放 Redis Hash，库存/券用 Redis 乐观锁或原子操作。
- **问题**：本地环境无 Redis；Redis 重启即丢；与「幂等由唯一索引」原则冲突。
- **修正**：购物车**落库**（`cart_item`，`uk_cart_line` 唯一索引 upsert，登录合并游客车）；库存/券并发安全改用数据库 CAS（`version` 乐观锁 \+ 唯一索引），**不依赖 Redis**。本文技术选型、关键机制设计已去除 Redis 强依赖。

### C-8 订单表缺时间线与幂等约束（中，已修正）
- **原文档**：`orders` 仅有 `created_at`，且要求「下单传 idempotent_key」「生成唯一取餐码」但表无对应约束。
- **问题**：无法渲染订单时间线；无唯一索引的幂等不可靠（并发会双写）；取餐码唯一域未定义。
- **修正**：补 `paid_at/accepted_at/ready_at/delivering_at/completed_at/cancel_at/refunded_at` 与 `order_status_log`；`idempotent_key` 唯一索引；`pickup_code + store_id + pickup_date` 联合唯一（按门店+当日喊号）。本文订单状态机与数据模型表已更新。

### C-9 用户券三态不可区分占用/在用（中，已修正）
- **原文档**：用户券仅 `UNUSED/USED/EXPIRED` 三态，正文又要求「下单即核销占用」「支付失败则释放」。
- **问题**：三态无法区分「被订单占用尚未支付」与「真正在用」，超时取消时无法判断该不该退回。
- **修正**：新增 `LOCKED` 占用态，四态 `UNUSED→LOCKED→USED`，任意非 `USED` 可被 `EXPIRED` 覆盖；`version` 乐观锁保证并发只占用一次。本文优惠券规则与验收标准已更新。

### C-10 优惠券范围/渠道/叠加字段缺失（中，已修正）
- **原文档**：`coupon` 用单 `scope` 字段表达「全场/分类/商品」，遗漏 `channels`，未定义与等级折扣叠加关系。
- **问题**：无法表达「多指定分类」；外卖/自取渠道无法限定；与等级折扣叠加歧义。
- **修正**：范围拆 `coupon_scope` 子表（`CATEGORY`/`PRODUCT` 多对多）；补 `channels`（适用渠道）、`stackable`（默认不叠加）。本文数据模型表与优惠券规则已更新。
